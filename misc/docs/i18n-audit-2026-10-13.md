## 二、主链路：已正确 ID-based

- 279 个调用点全部是 `qtTrId("key")` / `qsTrId("key")` 形态，**没有一处** `tr("中文")` / `translate(ctx, "中文")`。
- key 命名规则统一：`<模块>_<用途>`，带占位符的加 `_fmt` 后缀（如 `chat_tool_call_fmt`）。
- `.ts` 是标准 ID-based 结构：空 `<context><name></name>` + `<message id="...">`，且**无 `<source>`**
  （由 `misc/tools/release-translations.ps1` 的规范化步骤持续清理）。
- 源码里唯一的自然语言 key 校验盲点也已被注释说明（`TranslationManager.cpp:231-234` 的 `"中文"` 兜底显示名 ——
  这是**故意保留**的，改成从语言包取反而会在包缺失时把语言下拉显示成代号）。

**词法扫描与 lupdate 的差异只有 1 个**：`TranslationManager.h:3` 文档注释里的示例 `qtTrId("key")`。
条数以 lupdate 为准（220）。

## 三、发现 3（最要紧）：发布脚本的 key 校验漏掉整个 QML

`misc/tools/release-translations.ps1:117`：

```powershell
$code = Invoke-Quiet $lupdate @("-recursive", (Join-Path $root "source\src"), (Join-Path $root "source\include"), "-ts", $tmpTs)
```

QML 在 `source\qml`，**不在 lupdate 的输入里**。实测：

- lupdate 只喂 `source/src` + `source/include` → **116** 个 key
- lupdate 单独喂 `source/qml` → **117** 个 key
- 两者交集仅 13 → 并集 220
- 即 **104 个 QML 专用 key（占全部 key 的 47%）不在校验范围内**

模拟脚本当前会输出：`missing = 0`（侥幸对上）、`stale = 150` —— 其中 104 条其实是 QML 在用的 key，
被误判成"源码里已不存在"。

**风险**：以后新增一条 QML key（例如 `model_max_output`）而忘了写进 `.ts`，
脚本**不会报错**（因为它根本看不到这条 key），而 `qtTrId`/`qsTrId` 未命中会原样返回 id
⇒ 界面直接显示 `model_max_output` 这类代号。今天 missing=0 是运气，不是机制。

**修法**：把 `source\qml` 一并传给 lupdate，或改成对 `source` 整棵树做 `-recursive`。

## 附：复现方式

| 步骤 | 命令 |
|---|---|
| 抽 C++ key | `lupdate -recursive source/src source/include -ts %TEMP%\cpp.ts` |
| 抽 QML key | `lupdate -recursive source/qml -ts %TEMP%\qml.ts` |
| 校验 `.qm` 覆盖率 | 直接读二进制搜 key：**id 段是 UTF-8 明文**（译文段才是 UTF-16BE） |
| 找到"哪份 `.qm` 在生效" | 看 exe 在哪 —— `TranslationManager` 读 **exe 同目录的 `translations/`**，外部优先、qrc 保底 |
